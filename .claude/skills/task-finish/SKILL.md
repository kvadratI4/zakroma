# /task-finish $ARGUMENTS

Пройди **Definition of Done** из `docs/agent/WORKFLOW.md` по пунктам и отметь каждый в разделе «7. Итог» файла задачи (`[x]` или `[ ]` с причиной).

1. Полный прогон: все тесты backend и frontend, покрытие не ниже порогов, ruff/mypy/eslint/tsc чистые. Приведи краткий вывод (числа тестов, покрытие) в «7. Итог».
2. Каждый критерий приёмки → ссылка на тест(ы), которые его проверяют.
3. Документация — обнови то, что изменилось:
   - API → `docs/06-api.md` + перегенерированный клиент;
   - схема → `docs/db/schema.sql` (из `pg_dump --schema-only`), `docs/04-data-model.md`;
   - доменное правило (только согласованное) → `docs/05-domain-rules.md`;
   - новые команды/порядок запуска → раздел «Команды» в `CLAUDE.md`;
   - архитектурное решение → новый ADR + индекс `docs/adr/README.md`;
   - сводка в `docs/BACKLOG.md`.
4. **Уроки.** Перечисли оператору кандидатов в уроки, накопленных за задачу (замечания оператора, грабли окружения, ошибочные предположения). После подтверждения добавь их в `docs/agent/LESSONS.md` по формату. Если урок противоречит существующему — предложи заменить старый, а не добавлять второй.
5. **Отложенное** → предложи оператору новые строки для BACKLOG (ID, название, размер). Добавь только подтверждённые.
6. Статус задачи → `Review` (BACKLOG и файл задачи). В «6. Журнал сессий» — финальная запись.
7. В чат: 3–6 строк итога, список изменённых документов, предложенное сообщение для squash-коммита/PR. Не делай `git push` и merge.

После приёмки оператор сам переводит задачу в `Done` (или просит тебя это сделать).
