# 02. Требования

Идентификаторы требований (`FR-…`, `NFR-…`) используются в задачах [BACKLOG](BACKLOG.md) и в названиях тестов, чтобы было видно, какое требование покрыто.

Колонка **Этап**: `MVP`, `S2` (ввод), `S3` (рецепты), `S4` (аналитика/YouTube), `L` (позже).

Требования выводятся из ценностей [01-vision](01-vision.md#ценности): **учитываем наличие, а не потребление**; учёт следует быту (бытовые меры, повторяющиеся покупки); приложение предлагает — человек подтверждает. Решение — [ADR-0013](adr/0013-presence-tracking-household-measures.md) (2026-10-26, T-008r).

## Функциональные требования

| ID | Требование | Этап |
|---|---|---|
| FR-AUTH-01 | Регистрация по email и паролю (email — логин, без подтверждения по почте). Пароль ≥ 8 символов. | MVP |
| FR-AUTH-02 | Вход по email и паролю. Сессия хранится в httpOnly-cookie, живёт 180 дней и продлевается при использовании. | MVP |
| FR-AUTH-03 | Выход (завершение текущей сессии). | MVP |
| FR-AUTH-04 | Пользователь может сменить имя и пароль в профиле. | MVP |
| FR-AUTH-05 | Любой член дома может сгенерировать одноразовую ссылку сброса пароля для другого члена (24 часа). Почтовый сервер не нужен. | MVP |
| FR-AUTH-06 | Защита от перебора: не более 10 неудачных попыток входа на email за 15 минут. | MVP |
| FR-AUTH-07 | Вход через Яндекс ID / Telegram. | L |

| ID | Требование | Этап |
|---|---|---|

| FR-HH-02 | Член дома создаёт ссылку-приглашение (действует 7 дней, многоразовая, может быть отозвана). | MVP |
| FR-HH-03 | По ссылке-приглашению новый пользователь регистрируется и сразу попадает в дом; существующий — вступает в дом после входа. | MVP |
| FR-HH-04 | Все члены дома имеют одинаковые права на чтение и изменение всех данных дома. | MVP |
| FR-HH-05 | Член дома может переименовать дом и покинуть его. Дом без участников архивируется. | MVP |
| FR-HH-06 | Пользователь может состоять в нескольких домах и переключаться между ними; приложение помнит последний выбранный дом. | MVP (схема и API), UI — допустимо упрощённый |
| FR-HH-07 | Пользователь может создать дополнительный дом (квартира, дача). | MVP |

| ID | Требование | Этап |
|---|---|---|
| FR-LOC-01 | CRUD мест хранения дома. Каждое место имеет тип: `fridge`, `freezer`, `pantry`, `cellar`, `balcony`, `other`. | MVP |
| FR-LOC-02 | Порядок мест настраивается (сортировка). | MVP |
| FR-LOC-03 | Нельзя удалить место, в котором есть партии; можно — после перемещения или отметки «Закончилось». | MVP |

### Справочник и продукты дома (CAT)

| ID | Требование | Этап |
|---|---|---|
| FR-CAT-01 | Глобальный справочник категорий и типовых продуктов (~300 позиций) загружается из CSV миграцией. Справочник только для чтения. | MVP |
| FR-CAT-02 | Продукт дома создаётся из позиции справочника (копируются единица, режим учёта, бытовые меры, сроки, пороги, норма дома, место по умолчанию) или вручную. | MVP |
| FR-CAT-03 | Поиск продукта при вводе: по названию и синонимам, без учёта регистра и «ё/е», с опечатками (триграммы). Продукты дома показываются выше позиций справочника. | MVP |
| FR-CAT-04 | Пользователь редактирует продукт дома: название, категория, единица, режим учёта, бытовые меры, норма дома, сроки хранения, пороги. | MVP |
| FR-CAT-05 | Продукт дома можно архивировать (скрыть из поиска), если у него нет партий. | MVP |
| FR-CAT-06 | **Бытовые меры.** Глобальный словарь мер (пачка, пакет, стакан, ложка, ломтик, буханка, банка, пакетик…) с формами числа. У продукта — мера покупки («пакет 930 мл») и до двух мер использования («стакан 200 мл»); справочник предлагает их для каждой позиции, для своего продукта меры предлагаются по категории. Количество вводится и показывается в мерах, где это понятнее граммов. | MVP |
| FR-CAT-07 | **Норма дома**: «должно быть дома всегда, не меньше N <мер>» (хлеб — не меньше буханки). Только продукты с нормой попадают в «Покупки». Норма по умолчанию — из справочника. | MVP |

### Запасы (INV)

| ID | Требование | Этап |
|---|---|---|
| FR-INV-01 | Добавление: продукт, сколько (в мерах продукта — «2 пакета», точным или примерным количеством, **или** без количества — «есть»), место, срок годности, дата покупки. Все поля, кроме продукта, **заполнены заранее** (FR-INV-03) и правятся на том же экране. | MVP |
| FR-INV-02 | Если срок по упаковке не указан, он рассчитывается как примерный по сроку хранения продукта с учётом типа места (морозилка) и **сразу показывается** при добавлении («≈ до 17.11»). Примерный срок помечается в UI. | MVP |
| FR-INV-03 | «Как в прошлый раз»: место и количество последней покупки продукта, типовой срок; «Обычно покупаете» — продукты по частоте покупок. | MVP |
| FR-INV-04 | Добавление — один экран-список: один продукт или все покупки после магазина сохраняются одним действием. Черновик списка хранится на устройстве до сохранения. В S2 в этот же список попадают позиции чека. | MVP |
| FR-INV-05 | Отметки наличия из списка, 1–2 нажатия: «Закончилось», «Выбросить» (испортилось — отдельно от «закончилось»), необязательное списание мерой («−стакан», «½ пачки»). Отметка относится к продукту в месте. | MVP |
| FR-INV-06 | Отметка уровня для любого продукта (нет / почти нет / мало / нормально / много / избыток) с необязательным примерным количеством. Отметка человека главнее расчёта: старое количество после неё не учитывается. | MVP |
| FR-INV-07 | Отметка «вскрыто»: пересчитывает срок по сроку хранения после вскрытия. | MVP |
| FR-INV-08 | Перемещение партии (целиком или частично) между местами; при перемещении в морозилку/из морозилки примерный срок пересчитывается. | MVP |
| FR-INV-09 | Исправление партии (опечатка в количестве/сроке) без записи о потреблении (событие `adjust`). | MVP |
| FR-INV-10 | Все изменения запасов пишутся в журнал событий (кто, когда, что, сколько). Журнал виден в карточке продукта (свёрнут: главное в карточке — наличие). | MVP |
| FR-INV-11 | Одновременное редактирование одной партии двумя людьми не теряет данные: второй получает конфликт и актуальное состояние. | MVP |
| FR-INV-12 | **Проверка места** («Проверить холодильник»): все продукты места списком с текущим уровнем; изменения отмечаются по ходу, «Остальное на месте» запоминает время проверки. Место, которое давно не проверяли, мягко предлагается проверить. | MVP |

### Обзор и предупреждения (VIEW)

| ID | Требование | Этап |
|---|---|---|
| FR-VIEW-01 | Экран «Запасы»: продукты по местам или по видам (категориям); у продукта — уровень словом, количество в мерах, ближайший срок; по видам — сводка по всем местам («есть ли из чего сделать бутерброд»). | MVP |
| FR-VIEW-02 | Фильтры: место, вид, статус (просрочено, скоро испортится, почти нет, мало, избыток). Поиск по названию. | MVP |
| FR-VIEW-03 | Предупреждения в двух разделах (T-004): «Сроки» — просрочено → скоро испортится; «Покупки» — закончилось → почти нет → мало, затем «пока не покупать» (избыток), только для продуктов с нормой дома; при «почти нет» и «мало» — подсказка в мерах («≈ 5 пакетиков»). Данные — одним запросом `/attention`. | MVP |
| FR-VIEW-04 | Порог «скоро испортится» — настройка дома (по умолчанию 3 дня). | MVP |
| FR-VIEW-05 | Карточка продукта: наличие (уровень, сколько в мерах, где лежит и до какого срока), быстрые действия, норма дома, бытовые меры, история (свёрнута), настройки и пороги (свёрнуты). | MVP |
| FR-VIEW-06 | Приветствие на «Запасах» называет одно самое важное на сегодня (просрочено → последний день → закончилось нужное) и «ещё N» со ссылкой; если всё в порядке — «Всё основное есть». | MVP |

| FR-RCPT-02 | Сопоставление строк чека с продуктами дома: сначала по сохранённым сопоставлениям, затем LLM-предложение; пользователь подтверждает список перед добавлением. | S2 |
| FR-RCPT-03 | Подтверждённые сопоставления запоминаются. | S2 |
| FR-RCPT-04 | Фото чека без QR → распознавание через мультимодальную LLM (резервный путь). | S2 |
| FR-RCPT-05 | Повторный импорт того же чека запрещён (дедупликация по фискальным реквизитам). | S2 |

| FR-RCP-02 | «Что приготовить»: рецепты, отсортированные по доле имеющихся ингредиентов; приоритет рецептам со скоропортящимися продуктами. | S3 |

### Аналитика и YouTube (S4)

| ID | Требование | Этап |
|---|---|---|
| FR-YT-01 | Импорт рецепта по ссылке YouTube: описание ролика → LLM-структурирование; если рецепта нет в описании — анализ видео моделью с поддержкой видео. | S4 |
| FR-YT-02 | Кэш по ID видео; лимит импортов на пользователя в сутки. | S4 |
| FR-STAT-01 | Оценка «хватит примерно на…» и «обычно покупаете раз в …» — по покупкам и закрытию партий, без записей «съели» (см. [доменные правила §7.1](05-domain-rules.md#71-на-сколько-примерно-хватит)). | S4 |
| FR-STAT-02 | Доля выброшенного по продукту и мягкая подсказка покупать меньше («из 4 пачек творога 2 выброшены»), [§7.2](05-domain-rules.md#72-доля-выброшенного). | S4 |
| FR-STAT-03 | «Часто покупаете вместе»: после добавления продукта предложить то, что обычно покупают с ним. Главный путь ввода — чек, поэтому подсказка вторична; после пилота, когда накопится история. | L |

## Нефункциональные требования

### Удобство (UX)

| ID | Требование |
|---|---|
| NFR-UX-01 | Добавление продукта из справочника — ≤ 3 нажатия и ≤ 10 секунд для обученного пользователя; 10 привычных продуктов после магазина — ≤ 2 минут. |
| NFR-UX-02 | Отметка «Закончилось» или уровня — 1–2 нажатия из списка «Запасов». |
| NFR-UX-03 | Mobile-first: основная ширина 360–430 px; на ПК — адаптивная раскладка. Зоны нажатия ≥ 44×44 px. |
| NFR-UX-04 | Шрифт по умолчанию ≥ 16 px; контраст по WCAG AA; понятные русские формулировки без жаргона. |
| NFR-UX-05 | Тёмная и светлая темы: по умолчанию — по системной настройке, с ручным выбором «Как на устройстве / Светлая / Тёмная» на устройстве (T-009). |
| NFR-UX-06 | Все тексты интерфейса — через i18n-ресурсы (сейчас `ru`); даты и числа форматируются по локали; бытовые меры — с формами числа («1 пачка», «2 пачки», «5 пачек»). |
| NFR-UX-07 | Каждый экран и функция проходят вопросы-проверки [01-vision](01-vision.md#вопросы-проверки): удобно ли старшим, будет ли человек делать это в обычной жизни, упростит ли это ему жизнь. |

### Безопасность

| ID | Требование |
|---|---|
| NFR-SEC-01 | Только HTTPS (Caddy, автоматические сертификаты). HSTS. |
| NFR-SEC-02 | Пароли — Argon2id. Сессионный токен хранится в БД как хеш; cookie `HttpOnly; Secure; SameSite=Lax`. |
| NFR-SEC-03 | Защита от CSRF: SameSite=Lax + проверка заголовка `Origin` на изменяющих запросах. |
| NFR-SEC-04 | Каждый запрос к данным дома проверяет членство пользователя в доме (одна общая зависимость FastAPI, покрытая тестами). |
| NFR-SEC-05 | Секреты (ключи LLM, API чеков, БД) — только на сервере, в `.env` вне репозитория. Во frontend секретов нет. |
| NFR-SEC-06 | Лимиты частоты на вход, регистрацию и платные интеграции (LLM). |
| NFR-SEC-07 | Персональные данные (email, имя) хранятся на VPS в РФ. |
