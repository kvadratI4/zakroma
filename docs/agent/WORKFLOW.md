# Процесс разработки с агентом

Решение — [ADR-0009](../adr/0009-agent-workflow-tdd.md). Диаграмма состояний задачи — [diagrams/states.md](../diagrams/states.md).

## Роли

| Роль | Кто | Отвечает за |
|---|---|---|
| **Оператор** | человек | что делать и зачем, ответы на вопросы, приёмка, `git push`/merge, деплой, решения по ADR |
| **Агент** | Claude Code | как делать: предложение, тесты, код, обновление документации, фиксация уроков |

## Жизненный цикл задачи

```
BACKLOG (Ready)
  │  оператор: /task-start T-xxx
  ▼
Proposal ── агент: понимание, подход, файлы, ПЛАН ТЕСТОВ, риски, вопросы ──► СТОП
  │  оператор отвечает в чате (или правит файл задачи) и пишет: /task-implement T-xxx
  ▼
In progress ── агент: RED → GREEN → REFACTOR по каждому тест-кейсу; журнал в файле задачи
  │  всё зелёное
  │  оператор: /task-finish T-xxx
  ▼
Review ── агент: DoD, документация, уроки, отложенное ──► оператор проверяет
  │  ок → Done            замечания → обратно в In progress (+ урок)
  ▼
Done
```

Команды — навыки в `.claude/skills/`: `/next-task`, `/task-start`, `/task-implement`, `/task-finish`, `/lesson`.

## Definition of Ready (оператор, перед `Ready`)

- [ ] Понятно **зачем** (1–3 предложения или ссылка на требования FR/NFR).
- [ ] Есть критерии приёмки, проверяемые тестом (в BACKLOG или в файле задачи).
- [ ] Зависимости в `Done`.
- [ ] Размер S или M (L — разбить).

## Шаг 1. Предложение и вопросы

Выход агента — заполненные разделы 3 и 4 файла `tasks/T-xxx.md` и короткое сообщение в чат. **Код не пишется.**

Хороший вопрос агента:

```
2. Списание больше остатка: ошибка или обнулить партию?
   а) 422 unit_exceeds — строже, но раздражает при неточном вводе;
   б) обнулить и закрыть партию, вернуть clamped=true  ← рекомендую: так в доменных правилах §5.3, ввод дома неточный.
```

Плохой вопрос: «Как лучше сделать списание?» (без вариантов), или вопрос, ответ на который уже есть в документации.

## Шаг 2. Ответы оператора

Оператор отвечает в чате коротко («1 — б, 2 — да, 3 — сделай как предлагаешь»). Агент записывает ответы в таблицу вопросов файла задачи — это **память проекта**: через полгода видно, почему решено так.

Если ответ оператора — общее правило («никогда не добавляй зависимости без спроса», «кнопки делай крупнее»), агент предлагает записать его как урок.

## Шаг 3. Реализация (TDD)

Подробно — [08-testing.md](../08-testing.md#1-tdd-цикл-в-задаче) и навык `/task-implement`. Главное:

1. Тест → запуск → **падает по правильной причине** → код → зелёный → рефакторинг.
2. Неожиданное изменение контракта (API, схема, доменное правило, зависимость) → **стоп и вопрос**.
3. Мелкие решения — сам, с записью в «Решения в ходе реализации».
4. Идеи вне рамок — в «Отложено», не реализуются.
5. После каждого заметного шага — запись в «Журнал сессий»: что готово, что следующее. Это позволяет начать новую сессию (`/clear`) и продолжить без потерь.

## Definition of Done (агент проверяет в `/task-finish`, оператор — при приёмке)

- [ ] Все критерии приёмки покрыты тестами (ссылки в «Итоге»).
- [ ] Все тесты зелёные; покрытие не ниже порогов (08-testing §6).
- [ ] ruff, mypy --strict, eslint, tsc — без ошибок.
- [ ] Нет закомментированного кода, отладочных `print`/`console.log`, TODO без номера задачи.
- [ ] Тексты UI — через i18n; форматирование количеств/дат — через общие функции.
- [ ] Документация обновлена: API, схема, доменные правила, ADR, команды в CLAUDE.md — что затронуто.
- [ ] Новые маршруты дома в матрице проверок доступа.
- [ ] Уроки предложены и (после подтверждения) записаны.
- [ ] Отложенное предложено в BACKLOG.
- [ ] Статус `Review`, журнал задачи закрыт, предложено сообщение коммита/PR.

## Уроки (как не наступать на грабли дважды)

Источник уроков:

| Источник | Пример |
|---|---|
| Замечание оператора на ревью | «Не используй `float` для граммов» |
| Ответ оператора, выражающий общее правило | «Всегда спрашивай перед новой зависимостью» |
| Грабли окружения/библиотеки | «`DELETE` из stock_events падает из-за триггера — чистить `TRUNCATE`» |
| Ошибочное предположение агента | «Думал, `similarity` найдёт опечатку в длинной строке — нужен `word_similarity`» |

Куда писать:

| Что | Куда |
|---|---|
| Короткое правило, важное везде | `docs/agent/LESSONS.md` (загружается в каждую сессию через CLAUDE.md) |
| Правило только для части кода | `.claude/rules/<area>.md` (загружается при работе с этими файлами) |
| Многошаговая процедура | навык `.claude/skills/<name>/SKILL.md` |
| Почему принято решение | ADR или файл задачи |

Гигиена: `LESSONS.md` ≤ ~150 строк. Раз в этап (или когда файл разрастается) — `/lesson` предлагает объединить похожие и перенести устаревшие в архив.

Claude Code также ведёт собственную авто-память (локально у оператора). Она полезна, но **не заменяет** `LESSONS.md`: уроки проекта должны быть в репозитории — видимы, проверяемы и одинаковы на любом компьютере.

## Git

- Ветка на задачу: `t-xxx-short-name` от `main`.
- Conventional Commits по-английски: `feat(inventory): …`, `fix(auth): …`, `test: …`, `docs: …`, `chore: …`. В теле — `Refs: T-xxx`.
- Агент коммитит локально после зелёных циклов; `push`, PR и merge — оператор.
- `main` всегда зелёный и деплоится.

## Когда что-то пошло не так

| Ситуация | Действие агента |
|---|---|
| Тесты не запускаются из-за окружения | Описать ошибку, не «чинить» тесты; предложить исправление окружения |
| Требование противоречит доменным правилам / ADR | Стоп, показать противоречие, предложить варианты |
| Задача оказалась больше оценки | Стоп, предложить разбиение, сделанное зафиксировать в журнале |
| Оператор недоволен результатом | Уточнить, что именно не так; исправить; предложить урок |
