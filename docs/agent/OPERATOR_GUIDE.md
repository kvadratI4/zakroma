# Памятка оператору: как работать с Claude Code в этом проекте

## Подготовка (один раз)

1. Создать репозиторий на GitHub, положить в него содержимое этого архива, первый коммит в `main`.
2. Установить Claude Code и открыть его в корне репозитория. `CLAUDE.md`, `.claude/settings.json`, правила `.claude/rules/` и навыки `.claude/skills/` подхватятся автоматически.
3. Проверить, что агент видит контекст: спросить «Какие уроки проекта ты знаешь?» — он должен перечислить `L-001…`.
4. Прочитать и поправить [справочник](../catalog/README.md) — это единственная часть, где нужны ваши знания о семье.

Документация Claude Code: https://code.claude.com/docs (настройки, навыки, память).

## Типичная сессия

```
/next-task                       ← что можно брать
/task-start T-001                ← агент читает, пишет предложение и вопросы, останавливается
(вы отвечаете в чате: «1 — а, 2 — как предлагаешь, 3 — нет, не нужно»)
/task-implement T-001            ← тесты → код; агент спросит, если упрётся в контракт
/task-finish T-001               ← DoD, документация, кандидаты в уроки
(вы проверяете diff и файл tasks/T-001.md, отвечаете по урокам)
git push, PR, merge              ← вручную
/clear                           ← новая задача — с чистого контекста
```

Одна задача — одна-три сессии. Если сессия прервалась или контекст переполнился — `/clear` и «продолжи T-xxx по журналу»: агент восстановит состояние из файла задачи.

## Как давать замечания, чтобы они не терялись

- Разовое («здесь переименуй») — просто в чате.
- Правило на будущее («никогда не…», «всегда…») — `/lesson никогда не используй float для количеств`. Агент предложит формулировку, вы подтверждаете.
- Решение с последствиями («берём YandexGPT») — просите оформить ADR.

## Что проверять при приёмке (5 минут)

1. Файл задачи: понимание задачи совпадает с вашим замыслом; ответы на вопросы записаны верно.
2. План тестов ↔ критерии приёмки: ничего не пропущено.
3. Тесты читаются как спецификация; нет ослабленных старых проверок.
4. Diff: нет лишнего вне рамок задачи, нет новых зависимостей без согласования.
5. Документация обновлена (агент перечисляет, что менял).
6. Для UI — открыть на телефоне.

## Когда вмешиваться

| Признак | Что сделать |
|---|---|
| Агент начал писать код на `/task-start` | Остановить, напомнить L-001 |
| Вопросы без вариантов или ответ есть в docs | Указать документ; при повторе — урок |
| Агент «чинит» тест, чтобы он прошёл | Остановить, попросить объяснить причину падения |
| Задача разрастается | Попросить разбить, лишнее — в BACKLOG |
| Повторяется одна и та же ошибка | `/lesson`, проверить, что урок короткий и однозначный |

## Обслуживание раз в этап

- Пролистать `LESSONS.md`: убрать устаревшее, объединить похожее.
- Сверить BACKLOG со сводкой; пересмотреть порядок этапов (после пилота — T-044).
- Проверить восстановление из бэкапа (после T-042).
