# 0012. Prod-стек с минимальными правами: роли БД, сети, CSP

- Статус: Accepted
- Дата: 2026-10-25
- Задача: T-007

## Контекст

Стек на VPS (ADR-0002) хранит данные семьи и доступен из интернета. Оператор отдельно потребовал, чтобы база была недоступна извне, а пароли не попадали в репозиторий, образы и логи (T-003). Обзор безопасности в сводке 01 назвал ещё два пробела: заголовки безопасности и открытую OpenAPI-схему в prod. Компрометация одного звена — например, уязвимость в зависимости api — не должна давать доступа к остальным.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| Одна роль БД (суперпользователь `POSTGRES_USER`) для миграций и api | просто | взломанный api может менять схему, читать что угодно, создавать роли |
| Две роли: суперпользователь-владелец выполняет миграции + роль api | api без DDL | миграции работают с правами суперпользователя |
| **Три роли: суперпользователь только для инициализации, владелец без прав суперпользователя, роль api** | ни одна рабочая роль не суперпользователь; api не меняет схему | скрипт инициализации; ручная смена паролей |
| `style-src 'unsafe-inline'` в CSP | без правок кода | внедрённые стили остаются возможны |
| **Строгий CSP + токены темы через `adoptedStyleSheets`** | ни встроенных скриптов, ни стилей | одна правка в `main.tsx`; тема до загрузки JS (T-009) — через хеш |

## Решение

- **Роли** (`deploy/db-init/10-roles.sh`, только на пустом томе): `postgres` — инициализация; `zakroma_owner` — владелец базы и схемы, миграции (сервис `migrate`), не суперпользователь (`pg_trgm` — доверенное расширение); `zakroma_app` — данные (`SELECT`/`INSERT`/`UPDATE`/`DELETE` через default privileges), без DDL и доступа к базе `postgres`. Каждый сервис получает только свой пароль.
- **Сети:** `db` — `internal`, без выхода в интернет, доступна только `api` и `migrate`; наружу опубликованы только 80/443 Caddy; подсеть `web` закреплена, uvicorn доверяет `X-Forwarded-For` только из неё.
- **Контейнеры:** только чтение, `cap_drop: ALL` (Caddy — `NET_BIND_SERVICE`), `no-new-privileges`, непривилегированный пользователь api, образы по digest.
- **Caddy:** HSTS, `nosniff`, `Referrer-Policy: same-origin`, `Permissions-Policy`, CSP без `unsafe-inline`; лимит тела запроса к API 1 МБ; без access-лога (токены в путях); `X-Request-ID` ставит Caddy.
- **OpenAPI и Swagger** в prod не публикуются.
- Проверки: `tests/integration/test_db_roles.py`, `tests/smoke/test_prod_stack.py`, задача CI `prod stack`.

## Последствия

- Плюсы: взлом api не даёт менять схему и не открывает путь к суперпользователю; база не видна ни из интернета, ни из Caddy; правила проверяются тестами на каждом PR.
- Минусы / долг: `10-roles.sh` работает только на новом томе — смена паролей и ролей вручную (09-deployment §2.1); Caddy в контейнере — root (без привилегий, с файловой системой только для чтения); на внутреннюю таблицу `alembic_version` у роли api тоже есть права на запись (default privileges).
- Что нужно сделать: T-009 — скрипт темы в CSP по хешу; S2 — `camera=(self)` для сканера; T-041 — проверить подсеть `web` на VPS; T-042 — бэкап ролью с правами только на чтение.
