2. **Визуальные решения согласовывались «на словах»** (T-004). Стиль и меню, записанные как согласованные, оператор отклонил, не увидев их. Помогла страница-концепт с тремя вариантами: «Фарфор» выбран за один круг (L-023). Разделы меню переименованы по вопросам семьи (L-028).
3. **Свежие мажорные версии несовместимы между собой** (T-004, T-005). typescript-eslint требует TypeScript < 6.1, eslint-plugin-jsx-a11y — ESLint ≤ 9, `openapi-typescript` — TypeScript 5. Каждую версию проверяли экспериментом до установки, несовпадение разрешали явно, с записью в репозитории (L-025, L-026).
4. **Проверки выглядели зелёными, но не проверяли** (T-003…T-005):
   - покрытие с async SQLAlchemy считалось неверно (L-020);
   - MSW 3 молча игнорировал переименованную опцию (L-026);
   - клиент API ходил мимо MSW в реальную сеть (L-030);
   - проверка истории на секреты пропускалась без `--all-files` (L-022, L-029).

   Общий урок L-029: убеждаться, что проверка действительно выполнилась.
5. **Окружение Windows** (весь E0): `python3` — заглушка Microsoft Store, PATH терминала приложения не видит новые инструменты, дочерний `vite` переживает остановку задачи (L-014, L-016, L-032).

## 5. Независимая оценка

### 5.1. Безопасность — есть замечания

Сильные стороны:

- секреты не попадают в репозиторий: генерация паролей, `.gitignore`, запреты агенту читать `.env*`, gitleaks со своими правилами, проверка истории;
- все локальные сервисы слушают только `127.0.0.1` — проверено `netstat`;
- ответы и логи не раскрывают детали: тексты драйвера БД, введённые значения, query-строки;
- зависимости закреплены lock-файлами (`uv.lock`, `pnpm-lock.yaml`, установка `--frozen-lockfile`).

Риски и пробелы:

1. **Все проверки обходятся** `git commit --no-verify`, а `main` ничем не защищён: проверок на сервере нет, merge ручной. → T-006 (CI), затем защита ветки `main` в настройках GitHub (делает оператор).
2. **Нет проверки уязвимостей зависимостей** (Dependabot или `pip-audit` / `pnpm audit`). Сейчас ~10 прямых зависимостей backend и ~30 у frontend, транзитивных — сотни. → предложение 1.
3. **Цепочка поставки CI:** сторонние actions по плавающим тегам могут подменить код сборки. → решается в T-006 (вопрос о закреплении по SHA).
4. **OpenAPI-схема открыта в prod** (`/api/v1/openapi.json`; Swagger UI скрыт). Она раскрывает список маршрутов, хотя данных не содержит. Для семейного приложения риск низкий, а схема полезна для диагностики. → принять риск; пересмотреть в T-010, когда появятся маршруты дома.
5. **HTTP-заголовки безопасности** (CSP, HSTS, `X-Content-Type-Options`, `Referrer-Policy`) нигде не записаны. Их место — Caddy. → предложение 2 (критерий T-007).
6. Аутентификации пока нет. Это ожидаемо: единственный маршрут `/health` публичный по смыслу, вход появится в T-010.

### 5.2. Архитектура — хорошо

Сильные стороны:

- код следует принятым ADR: слои backend, `Clock` вместо системного времени, problem+json, один origin, генерируемый клиент (ADR-0008), изоляция тестов (ADR-0011);
- каждое решение записано (11 ADR, «Решения» в файлах задач);
- frontend и backend связаны контрактом, который проверяется автоматически, а не договорённостью.

Риски:

1. **Доменного слоя ещё нет** (T-030). Правила `app/domain` (чистота, покрытие 90 %) пока ничем не проверяются. → критерии уже есть в T-030; CI в T-006 должен быть готов добавить порог для `app/domain`, когда каталог появится.
2. **`app/core/openapi.py` дорабатывает схему, которую генерирует FastAPI**, и полагается на его внутреннее правило «когда ставится 422». Обновление FastAPI может это сломать. → тесты `test_openapi_schema.py` и хук `openapi-fresh` это поймают; принять риск.
3. **Связка инструментов:** frontend-скрипт вызывает `uv`, хуки — `uv` и `pnpm`. Поэтому в каждом окружении (CI, новая машина) нужны оба инструмента. → учесть в T-006; описано в README.
4. **Нагрузка на VPS пока не оценена** (память api, Postgres, Caddy на маленьком тарифе). → T-007 / T-041 (выбор тарифа по замеру prod-сборки).
