## 1. Описание (оператор)

Из BACKLOG: CI (GitHub Actions) — lint, typecheck, тесты с покрытием (пороги), сборка frontend, проверка OpenAPI.

Критерии, накопленные в BACKLOG из прошлых задач:

- **из T-001:** CI запускает `pre-commit run --all-files` — те же проверки, что локально;
- **из T-003, L-022:** CI проверяет историю git на секреты (`gitleaks-history --all-files`) и запускает интеграционные и миграционные тесты с Docker;
- **из T-004:** frontend — `pnpm install --frozen-lockfile`, `typecheck`, `lint`, `format:check`, `test` с покрытием (порог 08-testing §6), `build`, `pnpm size` ≤ 300 КБ;
- **из T-005:** `pnpm api:check` (нужны uv и Node в одной задаче).

## 2. Критерии приёмки (согласованы оператором 2026-10-24)

- **AC-1. Запуск и права.** `.github/workflows/ci.yml` запускается на PR в `main`, на push в `main` и вручную (вопрос 1).
  - Права токена — только чтение (`contents: read`), секреты не используются, `persist-credentials: false`.
  - Сторонние actions закреплены по полному SHA (вопрос 2).
  - Новый push в ту же ветку отменяет устаревший прогон.
- **AC-2. Задача `checks`:**
  - `pre-commit run --all-files` — ruff, eslint, prettier, YAML/JSON, gitleaks, справочник, `openapi-fresh` (= `pnpm api:check`), actionlint (вопрос 5);
  - `pre-commit run gitleaks-history --hook-stage manual --all-files` по **полной** истории (`fetch-depth: 0`).
- **AC-3. Задача `backend`:** `uv sync --frozen`, `mypy --strict`, `pytest --cov` — все тесты, включая интеграционные и миграционные на настоящем Postgres (testcontainers, Docker раннера); покрытие ≥ 80 %, иначе задача красная.
- **AC-4. Задача `frontend`:** `pnpm install --frozen-lockfile`, `typecheck`, тесты с покрытием ≥ 70 % (пороги в `vite.config.ts`, ниже — красная; вопрос 4), `build`, `pnpm size` ≤ 300 КБ. `lint` и `format:check` уже выполняет `checks`.
- **AC-5. Тесты не зависят от машины разработчика.** Ни один тест не читает `deploy/.env.dev`. На чистом Linux результат тот же, что у оператора на Windows (вопрос 6).
- **AC-6. Первый прогон.** На PR этой задачи все три задачи зелёные; время прогона записано в итог.
- **AC-7. Обновления и уязвимости зависимостей** (вопрос 3): `.github/dependabot.yml` для GitHub Actions, uv (backend) и npm/pnpm (frontend); в инструкции для оператора — включение Dependabot alerts и security updates (оповещения об уязвимостях и PR с исправлениями).
- **AC-8. Документация:**
  - `docs/09-deployment.md` §4 — какие задачи, как читать результат, что делать при красном;
  - `docs/08-testing.md` §6;
  - CLAUDE.md (новые команды);
  - README (значок CI);
  - инструкция по защите `main` (вопрос 7).

## 3. Предложение (агент, `/task-start`)

### 3.1. Понимание задачи

Сейчас все проверки только локальные: их можно обойти (`git commit --no-verify`), а `main` ничем не защищён. Сводка 01 называет это риском безопасности № 1. Нужен CI, который на каждом PR повторяет **те же** проверки, что у оператора на машине: pre-commit, типы, все тесты с порогами покрытия, сборку, размер бандла, актуальность API-клиента, историю git на секреты. Тогда merge можно разрешать только при зелёном CI. Деплой в задачу не входит — это T-041.

### 3.2. Подход

**Один workflow, три параллельные задачи** (каждая около 2–4 минут):

| Задача | Шаги | Почему отдельно |
|---|---|---|
| `checks` | uv + pnpm + `uv sync` + `pnpm install` → `pre-commit run --all-files` → `gitleaks-history --all-files` | одна точка для всех линтеров: локально и в CI одни и те же хуки (T-001) |
| `backend` | `uv sync --frozen` → `mypy` → `pytest --cov` (порог 80 % из `pyproject.toml`) | Docker и Postgres нужны только здесь |
| `frontend` | `pnpm install --frozen-lockfile` → `typecheck` → `test:coverage` → `build` → `size` | не ждёт backend |

**Окружение закреплено:**

- `ubuntu-24.04`, а не `ubuntu-latest`;
- uv 0.13.5 (как у оператора), Python — из `backend/.python-version` (3.13);
- Node — из `frontend/.nvmrc` (24), pnpm — из `packageManager` (12.15.0);
- `pre-commit==4.7.0`.

Кэш: uv по `uv.lock`, pnpm по `pnpm-lock.yaml`, окружения pre-commit по `.pre-commit-config.yaml`. Тайм-аут каждой задачи — 15 минут.

**Безопасность цепочки поставки** (репозиторий публичный):

- права токена только на чтение;
- только событие `pull_request`, не `pull_request_target`, — PR из форков не получают ни секретов, ни прав на запись;
- actions закреплены по SHA (вопрос 2), выбраны версии старше 7 дней:

| Action | Версия | SHA | Выпуск |
|---|---|---|---|
| `actions/checkout` | v7.0.1 | `3d3c42e5…` | 2026-07-20 |
| `astral-sh/setup-uv` | v10.3.0 | `1c37ad07…` | 2026-10-09 (v10.3.1/2 вышли 21–22.10 — слишком свежие) |
| `pnpm/action-setup` | v6.1.0 | `ea17c68d…` | 2026-09-05 |
| `actions/setup-node` | v7.1.0 | `949feb24…` | 2026-10-08 |
| `actions/cache` | v6.1.0 | `55cc8345…` | 2026-06-26 |

**Порог покрытия frontend** (вопрос 4): `@vitest/coverage-v8` той же версии, что Vitest (5.0.5), и скрипт `pnpm test:coverage`.

- В `vite.config.ts` — `coverage.include: src/**`. Исключения: тесты, `src/test/**`, сгенерированный `schema.d.ts`, точка входа `main.tsx` («UI-обёртки» по 08-testing §6).
- `thresholds`: строки, ветви, функции и операторы — по 70 %.

**Порог `app/domain` ≥ 90 %** (NFR-MNT-03) сейчас не ставлю: каталога ещё нет. Его добавит T-030 отдельным шагом `coverage report --include='app/domain/*' --fail-under=90` (критерий там уже есть).

**Тесты, зависящие от машины** (вопрос 6). Найдено на Linux-прогоне, подробности в §3.6.

- В `tests/conftest.py` — autouse-фикстура на всю сессию: отключает чтение `deploy/.env.dev` (`Settings.model_config["env_file"] = None`). Тесты не читают dev-пароль даже случайно.
- Подготовку трёх тестов это делает явной (L-019):
  - `test_logging.py` ×2 — `Settings(..., database_url=…)`;
  - `test_health.py::test_invalid_env_fails_at_startup` — `DATABASE_URL` из окружения, иначе тест проходит по чужой причине: падает на отсутствии URL, а не на `ENVIRONMENT=staging`.
- Сами проверки не меняются.

**actionlint** (вопрос 5): хук pre-commit `rhysd/actionlint` v1.7.12; pre-commit сам скачивает Go и собирает инструмент, Docker не нужен. Workflow нельзя запустить локально, поэтому без хука опечатка в нём видна только после push.

**Dependabot** (вопрос 3, предложение 1 сводки 01): `.github/dependabot.yml` — экосистемы `github-actions`, `uv` (`/backend`), `npm` (`/frontend`, понимает `pnpm-lock.yaml`).

- Раз в неделю, обновления сгруппированы по экосистеме, `cooldown` 7 дней: свежий выпуск не предлагается сразу, как в L-025.
- Каждое обновление приходит отдельным PR и проходит этот же CI. Merge, как всегда, за оператором.

**Уязвимости зависимостей** (ответ оператора на вопрос 3: «если критично — добавить»). Критично: репозиторий публичный, а у backend и frontend сотни транзитивных пакетов. Закрывается в этой задаче без новых инструментов:

- **Dependabot alerts** сверяют `uv.lock`, `pnpm-lock.yaml` и actions с базой уязвимостей GitHub (GitHub Advisory Database) и оповещают;
- **Dependabot security updates** сами открывают PR с исправленной версией — он проходит этот же CI;
- включаются в настройках репозитория (оператор, шаги — в той же инструкции, что защита `main`).

Отдельная задача пока не нужна. `pip-audit`/`pnpm audit` в CI дублировали бы ту же базу; если оповещения окажутся недостаточными, это строка «Позже».

**Защита `main`** (вопрос 7) — после первого зелёного прогона, в настройках GitHub (делает оператор):

- обязательный PR;
- обязательные проверки `checks`, `backend`, `frontend`;
- запрет force-push и удаления.

Пошаговая инструкция — в `docs/09-deployment.md` §4.

### 3.6. Риски, альтернативы, вне рамок

**Проверено экспериментом (L-017, L-029)** — на чистой копии `git archive HEAD` в Docker, без затрагивания проекта:

- **frontend на Linux** (`node:24-bookworm-slim`): `pnpm install --frozen-lockfile` с lock-файлом, созданным на Windows, проходит; typecheck, lint, format, 97 тестов, сборка — зелёные; размер 121,6 КБ.
- **backend на Linux** (`python:3.13-slim` + uv 0.13.5): ruff, mypy, `export_openapi --check` — зелёные. **Unit-тесты: 2 из 42 падают** (`test_logging.py`: `Settings()` → `database_url Field required`). У оператора они проходят только потому, что `Settings()` молча берёт `DATABASE_URL` из `deploy/.env.dev`, то есть тесты читали dev-пароль. Тот же источник заставляет `test_invalid_env_fails_at_startup` в CI проходить по чужой причине. CI упал бы на первом же прогоне → вопрос 6.
- **Покрытие frontend** (`@vitest/coverage-v8` 5.0.5 в черновой копии): строки 91 %, ветви 90 %, функции 95 % — порог 70 % проходит с запасом.
- **actionlint** 1.7.12 (Docker-образ, на черновике `ci.yml`): черновик проходит; опечатки `timeout-minute` и `github.refx` ловит с номером строки.
- Репозиторий **публичный** (`api.github.com/repos/kvadratI4/zakroma` → 200 без токена): минуты Actions бесплатны без лимита, но workflow и логи видны всем. Поэтому никаких секретов в CI: их и не нужно до деплоя (T-041).

**Риски:**

- **Workflow нельзя запустить до push.** Первый настоящий прогон — на PR оператора. Мера: actionlint, те же команды прогнаны на Linux в Docker. Если что-то всплывёт — исправление коммитом в тот же PR.
- **Сборка gitleaks и actionlint из исходников** (Go) в первом прогоне — плюс 1–2 минуты; дальше работает кэш pre-commit.
- **Лимиты Docker Hub** на скачивание `postgres:18` раннерами GitHub — низкий риск: у раннеров повышенные лимиты, одно скачивание за прогон.

**Альтернативы:**

- Один последовательный job: проще, но дольше (сумма вместо максимума).
- Запуск на каждый push в любую ветку: двойные прогоны при PR (вопрос 1).
- `act` для локального запуска workflow: новый инструмент на машине оператора, а эмуляция раннера неточная — не предлагаю.

**Вне рамок:**

- сборка образов и деплой (T-007, T-041);
- E2E Playwright в CI (T-043);
- порог `app/domain` (T-030);
- отчёты покрытия в PR и загрузка артефактов;
- проверка уязвимостей сверх Dependabot (`pip-audit`, `pnpm audit`).

**Применимые уроки:** L-003, L-015, L-016, L-017, L-018 (тесты не читают `.env.dev`), L-019 (подготовка трёх тестов), L-021, L-022, L-025 (cooldown, версии старше 7 дней), L-029.

## 5. Решения в ходе реализации

- **Изоляция тестов от `deploy/.env.dev`** — сессионная autouse-фикстура `no_dev_env_file` в `tests/conftest.py` (`pytest.MonkeyPatch.context()` + `setitem(Settings.model_config, "env_file", None)`). После неё у оператора воспроизвелись ровно те два падения, что на Linux: локальный прогон теперь совпадает с CI.
- **`test_invalid_env_fails_at_startup`:** кроме подготовки (`DATABASE_URL` в окружении) добавлен `match="environment"` — тест становится только строже. Без этого он проходил бы и при отсутствии URL. Проверено обратным опытом: с корректным `ENVIRONMENT` → `DID NOT RAISE`.
- **В `test_logging.py`** URL без пароля (`postgresql+asyncpg://zakroma@127.0.0.1:5432/zakroma`): логированию база не нужна, gitleaks и ruff S105 молчат.
- **Покрытие frontend:** исключены тесты, `src/test/**`, `schema.d.ts`, `main.tsx` (точка входа: только монтирует приложение). Итог — 96,8 % операторов, 94,6 % ветвей. Порог проверен обратным опытом: при 99 % для ветвей код выхода 1 и `ERROR: Coverage for branches (94.59%) does not meet global threshold (99%)`.
- **`lint` и `format:check` не повторяются в задаче `frontend`** — их выполняет `checks` через pre-commit (те же eslint и prettier).
- **Dependabot:** minor и patch группируются по экосистеме, major — отдельными PR (peer-диапазоны, L-025); `cooldown` 7 дней; префиксы коммитов `ci` / `chore(backend)` / `chore(frontend)`. Файл проверен разовым запуском `uvx check-jsonschema@0.35.0 --builtin-schema vendor.dependabot`, без добавления хука: проходит, а испорченный (`uvx`, `default-dayz`) отклоняется.
- **Инструкция по настройкам репозитория** — `docs/09-deployment.md` §4.3. Защита `main` через Rulesets: обязательный PR с 0 одобрений (оператор один), обязательные проверки трёх задач, ветка должна быть актуальной, запрет force-push и удаления. Плюс Dependabot alerts / security updates и права Actions.
- **Значок CI** в README.
