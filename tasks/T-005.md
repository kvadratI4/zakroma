## 1. Описание (оператор)

Из BACKLOG: экспорт OpenAPI и генерация клиента (`openapi-typescript` + `openapi-fetch`), проверка актуальности.

Критерий из T-004 (BACKLOG, «Критерии»): dev-прокси Vite `/api` → `http://127.0.0.1:8000` — frontend и backend работают вместе в разработке.

## 2. Критерии приёмки (согласованы оператором 2026-10-24)

- **AC-1. Экспорт схемы.** `backend/scripts/export_openapi.py` пишет схему FastAPI в `frontend/src/api/openapi.json`. Запуск без БД и без чтения `deploy/.env.dev`. Повторный запуск не даёт изменений: ключи отсортированы, UTF-8 без `\u`-экранирования, LF, перевод строки в конце. С флагом `--check` файл не пишется: код выхода 1 и понятное сообщение, если файл устарел.
- **AC-2. Генерация типов.** `pnpm gen:api` (из `frontend/`) экспортирует схему и генерирует `src/api/schema.d.ts` через `openapi-typescript`. Повторный запуск не даёт изменений.
- **AC-3. Проверка актуальности.**
  - Изменение API без перегенерации роняет `uv run pytest`: тест сравнивает схему приложения с закоммиченным `openapi.json`.
  - Тот же дрейф роняет `pnpm api:check`: схема из backend, затем `schema.d.ts` по `openapi.json`.
  - CI подключит обе проверки в T-006.
- **AC-4. Клиент.** `src/api/client.ts` — типизированный клиент `openapi-fetch` на `paths` из `schema.d.ts`.
  - Обращение к несуществующему пути или полю ответа — ошибка `tsc`; проверяется `@ts-expect-error` в тесте.
  - Ответ 200 даёт типизированные данные.
  - Ответ problem+json (например, `503 db_unavailable`) даёт ошибку с `code`.
  - Ручных типов API во frontend нет.
- **AC-5. Ошибки в схеме** (вопрос 2). OpenAPI описывает ошибки так, как их реально отдаёт сервер:
  - схемы `Problem` и `ValidationProblem` (с полем `errors`) в формате `application/problem+json`;
  - стандартная схема FastAPI `422 HTTPValidationError`, которой у нас на деле нет, из схемы убрана;
  - у `/health` описан ответ `503`.
- **AC-6. Dev-прокси.** `pnpm dev` (и `pnpm preview`, вопрос 6) проксирует `/api` на `http://127.0.0.1:8000`. Страница на `127.0.0.1:5173` получает `/api/v1/health` от запущенного backend. Vite по-прежнему слушает только `127.0.0.1`.
- **AC-7. Документация и правила.** Обновить:
  - команды в CLAUDE.md и README;
  - ADR-0008 (как проверяется актуальность);
  - `.claude/rules/frontend.md` (как вызывать API, как мокать);
  - `docs/03-architecture.md` §3 (`src/api/`);
  - `docs/08-testing.md` §6–7.

## 3. Предложение (агент, `/task-start`)

### 3.1. Понимание задачи

Нужна связка «backend описывает API → frontend получает типы автоматически»: ADR-0008, NFR-MNT-04. Сейчас она должна заработать на единственном маршруте `/health`, чтобы с T-010 (вход, регистрация) каждый новый маршрут сразу попадал во frontend с типами. Расхождение должно ловиться автоматически, а не на ревью. Заодно frontend и backend начинают работать вместе в разработке через прокси Vite: это перенесено из T-004.

### 3.2. Подход

**Экспорт (backend).** `scripts/export_openapi.py`:

- строит приложение через `create_app()` с явными настройками без файла окружения (`_env_file=None`, `environment="test"`) и заглушкой `DATABASE_URL` без пароля;
- движок SQLAlchemy ленивый, к БД скрипт не подключается — проверено на машине;
- пишет `app.openapi()` через `json.dumps(sort_keys=True, ensure_ascii=False, indent=2)` с переводом строки в конце;
- флаг `--check` сравнивает с файлом и ничего не пишет;
- функция `render_openapi(app) -> str` общая для скрипта и pytest-теста.

**Имена операций (мелкое решение, вопрос 5).** Сейчас FastAPI генерирует `get_health_api_v1_health_get`; предлагаю брать имя функции маршрута (`get_health`) через `generate_unique_id_function`. Имена станут читаемыми в `schema.d.ts`, а пути от этого не меняются.

**Ошибки в схеме (вопрос 2).** Pydantic-модели `Problem` и `ValidationProblem` описывают то, что уже отдаёт `app/core/errors.py`.

- Роутер `/api/v1` объявляет общие ответы: `422` → `ValidationProblem`, `default` → `Problem`, тип `application/problem+json`. Код FastAPI проверен: если у маршрута уже объявлен `422`/`4XX`/`default`, свой `HTTPValidationError` он не добавляет.
- У `/health` — `503`.
- Поведение сервера не меняется, меняется только описание.

**Генерация (frontend).** Скрипты `package.json`:

- `gen:api` — `uv run --project ../backend python ../backend/scripts/export_openapi.py && openapi-typescript src/api/openapi.json -o src/api/schema.d.ts`;
- `api:check` — то же с `--check`; у `openapi-typescript` есть встроенный `--check`, проверено: код выхода 0 на свежем файле и 1 на изменённом.

**Клиент.** `src/api/client.ts`:

- `createClient<paths>({ baseUrl: window.location.origin })` — тот же origin: в dev через прокси, в prod через Caddy (03-architecture: один origin);
- небольшая функция `problemCode(error)` достаёт `code` из problem+json для перевода через i18n;
- хуки TanStack Query поверх клиента пишутся в задачах экранов (T-014 и далее); в T-005 их нет — не пишем код без потребителя.

**Прокси.** В `vite.config.ts`: `server.proxy` и `preview.proxy` `{ "/api": "http://127.0.0.1:8000" }`.

- Без `changeOrigin`: заголовок `Origin` останется `http://127.0.0.1:5173`, и в T-010 его нужно будет внести в список разрешённых для dev.
- Проверка — живой запуск backend + `pnpm dev` и запрос с 5173, плюс unit-тест конфигурации.

**Существующий тест.** `src/test/msw.test.tsx` содержит ручной `interface Health` — это прямо запрещено NFR-MNT-04 после появления клиента. Перевожу его на сгенерированный клиент; меняется только способ запроса, проверка «ответ MSW дошёл через TanStack Query» та же. Это изменение существующего теста — вопрос 3.

### 3.6. Риски, альтернативы, вне рамок

**Проверено экспериментом (L-017, L-025)** — в черновой папке, не в проекте:

- `openapi-typescript` 7.13 (последняя; `next` = 7.0.0-rc — старее) объявляет peer `typescript ^5.x`, у нас TS 6.0.3.
  - Генерация на TS 6 работает.
  - Клиент проходит `tsc` с нашими флагами (`strict`, `exactOptionalPropertyTypes`, `verbatimModuleSyntax`), `@ts-expect-error` на чужой путь срабатывает.
  - Вывод детерминирован.
  - pnpm только предупреждает; `peerDependencyRules.allowedVersions` в `pnpm-workspace.yaml` снимает предупреждение — проверено: `pnpm peers check` → «No peer dependency issues found».
- FastAPI 0.161 отдаёт OpenAPI **3.1.0**; `openapi-typescript` 7 его поддерживает. Схема строится без подключения к БД.
- `openapi-fetch` — около 17 КБ без сжатия, единицы КБ в gzip. В первый экран он попадёт только с первым реальным запросом; лимит 300 КБ не под угрозой.

**Расхождение версий: оценка риска** (вопрос оператора, 2026-10-24):

- Это не отклонение от плана. Архитектура задаёт «TypeScript strict» без версии; TS 6.0.3 выбран в T-004 (L-025). Генератор просто ещё не обновил объявленную совместимость под TS 6.
- `openapi-typescript` использует TypeScript только во время `pnpm gen:api`: строит и печатает `.d.ts`. В собранное приложение он не попадает. `openapi-fetch`, который работает в браузере, от TypeScript не зависит.
- Результат генерации — обычный `.d.ts`, его проверяет наш `tsc` 6 со всеми строгими флагами. Ошибочный вывод не пройдёт `pnpm typecheck`.
- Худший случай — будущая версия TS 6.x ломает генератор. Тогда `gen:api` падает с ошибкой или `api:check` показывает дрейф. Тихой порчи быть не может: версии зафиксированы в `pnpm-lock.yaml`, сами по себе не меняются. Выход: оставить прежнюю версию TS или дать генератору свой TypeScript 5 через `packageExtensions`/алиас — около 15 минут.
- На будущее: TypeScript 7 (компилятор на Go) меняет программный API компилятора. Переход на TS 7 потребует версии `openapi-typescript`, которая его поддерживает. Это отдельное решение при обновлении, а не риск T-005.

**Риски:**

- Хук и `gen:api` вызывают `uv` из frontend-скрипта. На машине оператора это работает так же, как хуки ruff; в терминале агента нужен PATH (L-016).
- Обновление FastAPI может поменять схему без изменения нашего кода. Тогда проверка упадёт — так и задумано: перегенерировать.

**Альтернативы:**

- `openapi-react-query` (0.5.4) — готовые хуки поверх `openapi-fetch`. Не предлагаю: ещё одна зависимость версии 0.x ради нескольких строк обёртки.
- `orval`, `hey-api` — тяжелее и противоречат ADR-0008.
- Понизить TypeScript до 5.x — шаг назад ради предупреждения.

**Вне рамок:**

- CI (T-006);
- хуки запросов экранов и перевод `code` ошибок в тексты (появятся с первыми экранами, T-014);
- разрешённый `Origin` для dev (T-010);
- Docker-сборка (T-007).

**Применимые уроки:** L-003, L-016, L-017, L-018 (экспорт не читает `.env.dev`), L-019 (правка подготовки `msw.test.tsx`), L-022 (заглушка DSN без пароля), L-025, L-026, L-027.

## 5. Решения в ходе реализации

- **Ошибки в схеме — дообработкой схемы FastAPI** (`app/core/openapi.py`), а не через `responses=` на роутере. Если объявить `default` на роутере, FastAPI перестаёт сам добавлять `422` к маршрутам, у которых есть что проверять; если объявить `422` на роутере, он появится и у `/health`, где проверять нечего. Поэтому `422` FastAPI по-прежнему ставит сам, а мы заменяем его схему на `ValidationProblem`, добавляем `default` → `Problem` и регистрируем схемы через `models_json_schema`. Ошибки сценариев маршрут объявляет сам через `problem_response(...)` (у health — `503`).
- **`Problem.detail` описан как необязательная строка без `default`.** `problem_body` не шлёт `detail: null`, а пропускает поле. Описание pydantic по умолчанию (`anyOf string|null`, `default: null`) `openapi-typescript` превращал в **обязательное** поле `detail: string | null`. Это нашёл `tsc` на тесте клиента, исправлено тестом в backend (`test_problem_detail_is_optional_string_without_default`).
- **Клиент берёт `fetch` в момент вызова** (`fetch: (request) => globalThis.fetch(request)`). `openapi-fetch` по умолчанию запоминает `globalThis.fetch` при создании клиента, то есть при импорте, до того как MSW подменит `fetch` в `beforeAll`. Тест тогда ушёл в настоящую сеть (`ECONNREFUSED 127.0.0.1:3000`) мимо MSW, и `onUnhandledFrame: "error"` этого не поймал.
- **Экспорт** — `python -m scripts.export_openapi` из `backend/` (`uv run --directory ../backend` в скриптах frontend): так пакет `app` импортируется без правки `sys.path`. Заглушка `DATABASE_URL` без пароля (L-022), `_env_file=None` (L-018).
- **`pnpm-workspace.yaml`** в `frontend/` — только для `peerDependencyRules` (pnpm 12 читает настройки оттуда; рабочей области из нескольких пакетов нет). Lock-файл: версии существующих пакетов не изменились, поменялся только суффикс peer-зависимости `supports-color` (7 → 10, её приносит `openapi-typescript`).
- **Тест конфигурации Vite** лежит рядом с ней (`frontend/vite.config.test.ts`, добавлен в `tsconfig.node.json`) в среде jsdom: общий `setup.ts` рассчитан на `window`, а директива `@vitest-environment node` ломала его. Это была первая, ложная причина RED.
